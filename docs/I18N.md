# Automoción OS — Internationalization (ES / EN)

Companion to `ARCHITECTURE.md`. Spanish (Colombia) and English are **both first-class**.
This document defines how, and what "works well" means concretely.

---

## 1. The standard

A language toggle "works well" when all eight of these hold. Anything less is a half-toggle,
which is worse than no toggle because it looks broken:

1. **Every visible string** switches — including validation errors, empty states, toasts, PDF
   text, emails, chatbot replies and 404 pages. Not just navigation.
2. **Database content switches** — blog posts, legal pages, FAQs, add-on names, milestone
   labels, document names. This is the part that is usually forgotten.
3. **Nothing is ever blank.** A missing translation falls back visibly and predictably, never
   to an empty string or a raw key.
4. **The URL carries the locale**, so a link shared in English opens in English.
5. **Switching preserves context** — same page, same filters, same scroll position. Never a
   bounce to the homepage.
6. **Formatting follows the locale** — dates, numbers and money, via `Intl`, never by hand.
7. **SEO is correct** — `hreflang` alternates, per-locale sitemaps, localized metadata.
8. **A missing key fails CI**, so the second locale cannot silently rot as the product grows.

---

## 2. Locales

| Locale | Code | URL prefix | Role |
|---|---|---|---|
| Español (Colombia) | `es-CO` | `/es` | **Default.** The client, their buyers and their market. |
| English (US) | `en-US` | `/en` | Foreign suppliers, expat buyers, the client's international counterparties. |

Short codes (`es`, `en`) appear in URLs; full locales (`es-CO`, `en-US`) drive `Intl`
formatting. The default locale **is** prefixed (`/es/catalogo`, not `/catalogo`) — an
unprefixed default creates duplicate-content ambiguity and makes the switcher's return path
inconsistent. One rule, no exceptions, is worth the extra three characters.

Adding a third locale (pt-BR, say) must be a config change plus a catalog, never a code change.

---

## 3. Library

**`next-intl`.** App Router native, works in Server Components (so the catalog stays
server-rendered), ICU MessageFormat for plurals and gendered strings, built-in `Intl`
formatters, and first-class localized pathnames. Alternatives considered: `next-i18next`
(Pages Router era), `lingui` (heavier tooling), Paraglide (compile-time, excellent but its
RSC story is younger than this project can absorb).

---

## 4. URL strategy — localized pathnames where they earn it

Public marketing and shop routes get **translated path segments**, because those URLs are
indexed and shared. Portal and admin routes keep canonical Spanish paths, because they sit
behind auth where SEO is irrelevant and a stable path is worth more than a translated one.

```ts
// src/i18n/routing.ts
export const routing = defineRouting({
  locales: ["es", "en"],
  defaultLocale: "es",
  localePrefix: "always",
  pathnames: {
    "/": "/",
    "/catalogo":            { es: "/catalogo",            en: "/catalog" },
    "/catalogo/[slug]":     { es: "/catalogo/[slug]",     en: "/catalog/[slug]" },
    "/comparar":            { es: "/comparar",            en: "/compare" },
    "/simulador":           { es: "/simulador",           en: "/import-calculator" },
    "/checkout":            { es: "/checkout",            en: "/checkout" },
    "/como-trabajamos":     { es: "/como-trabajamos",     en: "/how-it-works" },
    "/mapa-global":         { es: "/mapa-global",         en: "/global-map" },
    "/blog":                { es: "/blog",                en: "/blog" },
    "/blog/[slug]":         { es: "/blog/[slug]",         en: "/blog/[slug]" },
    "/nosotros":            { es: "/nosotros",            en: "/about" },
    "/contacto":            { es: "/contacto",            en: "/contact" },
    "/faq":                 { es: "/faq",                 en: "/faq" },
    "/legal/[slug]":        { es: "/legal/[slug]",        en: "/legal/[slug]" },
    // portal and admin: identical in both locales
  },
});
```

`config/routes.ts` (the typed route registry from `ARCHITECTURE.md` §4) wraps `next-intl`'s
navigation APIs, so **application code never writes a path or picks a locale** — it calls
`routes.vehicle(slug)` and gets the right URL for the active locale. The registry pattern and
localized pathnames fit together exactly; this is the payoff for not hardcoding URLs.

Route group structure becomes `src/app/[locale]/(marketing)/…`, `[locale]/(shop)/…`, etc.

**Dynamic slugs are translated too.** A `Post` has a per-locale slug, so
`/es/blog/aranceles-vehiculos-electricos` and `/en/blog/ev-import-duties` are the same record.
The switcher resolves the counterpart slug from the database, never by string manipulation.

## 5. Negotiation and persistence

Middleware resolves the locale in strict precedence:

1. Explicit locale in the URL (always wins — a shared link is unambiguous)
2. `User.preferredLocale` for an authenticated user
3. `NEXT_LOCALE` cookie
4. `Accept-Language` header
5. `es` (default)

Switching writes the cookie and, for signed-in users, persists to `User.preferredLocale` so
the choice follows them across devices. The middleware chain runs `intlMiddleware` **before**
the auth guard, so redirects preserve the locale prefix.

## 6. Message catalogs

```
src/messages/
├── es/
│   ├── common.json        shared: actions, states, validation, units
│   ├── navigation.json
│   ├── marketing.json
│   ├── catalog.json       includes the 21 filter labels
│   ├── pricing.json       every CostStage code has a label + tooltip here
│   ├── checkout.json
│   ├── portal.json
│   ├── admin.json
│   ├── pdf.json
│   └── email.json
├── en/  (identical key tree)
└── index.ts               loader + generated types
```

Namespaces mirror the module map, so a module owns its copy the way it owns its code.

Keys are typed end to end — `t("catalog.results.count")` autocompletes and a typo is a compile
error. ICU handles plurals and interpolation:

```json
{
  "results": { "count": "{count, plural, =0 {Sin resultados} one {# vehículo} other {# vehículos}} disponibles" },
  "shipping": { "shared": "Compartiendo contenedor con {others, plural, one {# vehículo más} other {# vehículos más}}" }
}
```

**The pricing catalog is special.** Every `CostStage.code` (`TAX.ARANCEL`, `FREIGHT.OCEAN`, …)
maps to a label and an explanatory tooltip in both locales. Because the stage registry drives
the PDF and the breakdown accordion, adding a cost line means adding two catalog entries — and
CI fails if you add the stage and forget the English one.

## 7. Translating database content

Two patterns, chosen per entity by whether the content needs its own URL and index.

**Pattern A — translation tables.** For content with slugs, SEO and querying:
`Post`, `Page`, `Category`, `Tag`, `FaqEntry`.

```prisma
model Post {
  id           String            @id @default(cuid())
  status       PostStatus
  publishedAt  DateTime?
  coverImageId String?
  translations PostTranslation[]
}

model PostTranslation {
  id        String  @id @default(cuid())
  postId    String
  locale    String              // "es" | "en"
  slug      String
  title     String
  excerpt   String
  body      Json                // rich text
  seoTitle  String?
  seoDesc   String?
  post      Post    @relation(fields: [postId], references: [id], onDelete: Cascade)

  @@unique([postId, locale])
  @@unique([locale, slug])      // slugs unique per locale
  @@index([locale, slug])
}
```

**Pattern B — `LocalizedText` JSONB.** For short operator-authored labels where a table would
be overkill: `AddOnProduct.name/description`, `TariffRule.legalBasis`, `DocumentRequirement.name`,
`TrackingMilestone.label`, `Brand.tagline`, parameter source notes.

```prisma
/// { "es": "Matrícula y placas", "en": "Registration and plates" }
name Json
```

with a core value object that owns resolution and fallback:

```ts
// core/i18n/localized-text.ts
export function resolve(text: LocalizedText, locale: Locale): Resolved {
  const value = text[locale];
  if (value) return { value, fallback: false };
  const fb = text[FALLBACK_CHAIN[locale]];          // en → es, es → en
  return { value: fb ?? "", fallback: true, fallbackFrom: FALLBACK_CHAIN[locale] };
}
```

**The fallback rule.** Missing translation → show the fallback locale's text, never a blank and
never a raw key. On the public site it renders plainly. In the admin it renders with a
`--warning` "sin traducir" pill, so operators can see and fix the gap. `Vehicle` spec *values*
are enums and numbers — they need no translation, only their labels do, which live in the
`catalog` catalog.

## 8. Formatting

All formatting goes through `next-intl`'s formatter — **`Intl` only, never manual string work.**

| | es-CO | en-US |
|---|---|---|
| Money (COP) | `COP $ 185.400.000` | `COP 185,400,000` |
| Money (USD) | `US$ 42.500` | `US$ 42,500` |
| Date | `12 de octubre de 2026` | `October 12, 2026` |
| Short date | `12/10/2026` | `10/12/2026` |
| Number | `1.234,56` | `1,234.56` |
| Days | `45 días hábiles` | `45 business days` |

Three rules that matter here:

- **The currency never changes with the locale.** An English-speaking buyer importing to
  Colombia still pays COP. Locale changes the *format*, not the money. Mixing that up would be
  a serious bug, so `Money` carries its currency and the formatter only decides presentation.
- **The currency code is always shown**, because this product puts USD and COP on the same
  screen constantly.
- **Tabular numerals everywhere**, in both locales — separators differ in glyph, not in width.

Units stay metric in both locales (km, kWh, kg). Colombia is metric and the vehicles are
specified metric; converting for English readers would corrupt comparisons against the
catalog data.

## 9. Surfaces beyond the UI

| Surface | Locale source | Notes |
|---|---|---|
| **Smart PDF** | `Quote.locale`, stored at creation | A quote issued in English re-downloads in English forever. Part of the immutable snapshot. |
| **Transactional email** | `User.preferredLocale`, else the quote/order locale | Templates in `messages/*/email.json` |
| **Chatbot** | Conversation locale, seeded from the page | System prompt pins the reply language; the locale is stored on `ChatConversation` |
| **OG / social cards** | `?locale=` on the render route | `/api/og/vehicle/[id]?locale=en` |
| **Instagram fichas** | Selected in `/admin/social` | Independent of UI locale — marketing may target either audience |
| **Channel feeds** | **Always `es-CO`** | TuCarro, CarroYa and Marketplace are Colombian. This is hardcoded *by intent* and documented in the adapter. |
| **Sitemaps** | One per locale + an index | |
| **Legal pages** | Both, with a Spanish-prevails clause | Colombian law governs; the ES text is authoritative |

## 10. SEO

- `alternates.languages` on every public page → `hreflang="es-CO"`, `hreflang="en-US"`,
  `hreflang="x-default"` → `/es`
- Self-referencing canonical per locale
- `sitemap-es.xml`, `sitemap-en.xml`, `sitemap.xml` index
- Localized metadata, OG title/description and OG image per locale
- `<html lang>` set from the active locale
- JSON-LD (Product, Article, Organization) emitted in the active locale

## 11. The switcher

Lives in the public header (and portal/admin topbars) as a compact `ES | EN` segmented control
— not a flag. Flags denote countries, not languages, and would wrongly imply US pricing.

Behavior: preserves the current route, all search params (so `/catalogo` keeps its 21 filters),
the hash and the scroll position. For a dynamic route it resolves the counterpart slug from the
database; if a translation genuinely does not exist for that record, it routes to the section
index in the target locale and shows a toast explaining why — it never 404s.

Rendered as real `<a href>` links to both locales, so crawlers see them.

## 12. Design implications

Spanish runs **15–25% longer than English**. Every layout in `PAGES-SPEC.md` is designed
against the Spanish string, so English can only get shorter.

Consequences already folded into the specs: no fixed-width buttons (padding, not width); nav
items must survive `"Cómo trabajamos"` vs `"How it works"`; table headers wrap to two lines
rather than truncate; the `/checkout` stepper labels are short in both; **no text baked into
images**; and the `TrafficLight` component labels sit beside the lamps rather than inside them.

A visual regression check renders four key screens in both locales at 390px and 1440px.

## 13. Admin translation workflow

Content editors get a **locale tab strip** at the top of the blog editor, page editor and any
form with `LocalizedText` fields. Each tab shows a completeness dot: filled when translated,
`--warning` hollow when falling back.

- `/admin/blog/[id]` — ES and EN tabs, each with its own slug, title, body and SEO block;
  publish state is shared, so a post cannot go live in one locale only unless explicitly allowed
- `/admin/parametros` — the `legalBasis` and source-note fields get inline ES/EN sub-inputs
- `/admin/ajustes` — a **translation status panel** listing every entity with a missing
  translation, as a work queue

## 14. Enforcement

Added to the CI pipeline from `ARCHITECTURE.md` §8:

- **Key parity check** — a script diffs the key trees of `messages/es` and `messages/en`.
  A key present in one and missing in the other **fails the build**. This is the single check
  that keeps the second locale from rotting.
- **ICU validation** — every message parses, and interpolation variables match across locales.
- **`no-literal-string`** already bans hardcoded copy in components; it now also covers
  `app/**` metadata exports.
- **Stage-label coverage test** — every `CostStage.code` in the registry has a label and tooltip
  in both catalogs.
- **Enum-label coverage test** — every Prisma enum value used in the UI has a label in both.
- **Route parity** — every entry in `pathnames` has both locales defined.
- **Smoke test** — the ten highest-traffic routes render in both locales without a missing-key warning.

## 15. Changes to the plan

- **M0 (+6h):** `next-intl` setup, `[locale]` route group, middleware chain, routing/pathnames
  config, catalog scaffolding with typed keys, formatters, the switcher component, and the key
  parity + ICU checks in CI — **before any page is written**, so no screen is ever built
  monolingual and retrofitted.
- **M1 (+3h):** translation tables (`PostTranslation`, `PageTranslation`, `CategoryTranslation`,
  `FaqEntryTranslation`), the `LocalizedText` core type and resolver, `User.preferredLocale`,
  `Quote.locale`, `ChatConversation.locale`; seed data authored in both locales.
- **M3 (+2h):** admin locale tab strip + completeness dots.
- **M5 (+1h):** PDF renders from `Quote.locale`.
- **M8 (+4h):** marketing and blog content in both locales, `hreflang`, per-locale sitemaps,
  localized metadata and OG images.
- **Testing (+2h):** parity checks, both-locale smoke test, visual regression at two widths.

**+18h. Revised project total: ~198h.**

The order matters more than the hours: i18n is set up in M0, before the first page exists.
Retrofitting two locales onto 42 finished screens costs several times this.
